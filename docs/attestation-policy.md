# Identity Attestation Policy

## Purpose

Attestation is the recurring process of confirming that an identity's
owner still requires the access assigned to them. Static access that
is granted once and never reviewed is a common source of privilege
creep and forgotten service accounts. This policy defines how
attestation cycles run in this environment and ties directly into the
rotation policy defined in rotation-policy.md.

## Cycle Length

Attestation requests are sent to identity owners with a 30 day
response window. This mirrors common enterprise practice, giving
owners enough time to respond without letting stale access linger
indefinitely.

## Response Handling

Each identity's owner can respond in one of three ways:

- **Approved** - the owner confirms the access is still required.
  No further action is taken until the next cycle.
- **Rejected** - the owner confirms the access is no longer needed.
  The identity is queued for removal in the next maintenance window.
- **No Response** - the owner did not respond by the due date.
  This is treated as the highest priority finding, since unconfirmed
  access is a governance risk. These identities are escalated for
  manual review.

In this lab environment, owner responses are simulated using a
weighted random outcome, 70 percent Approved, 10 percent Rejected,
and 20 percent No Response, since there are no real coworkers to
respond to attestation requests. This is documented here for
transparency. In a production environment, this step would be
replaced with a real notification integration, for example email
or a ticketing system, and actual owner responses.

## Report Location

Each attestation cycle produces docs/attestation_report.md, a
markdown report summarizing approval rates and individually listing
every identity in the No Response and Rejected categories. This
report is regenerated by running scripts/attestation_report.py after
scripts/attestation_generator.py and
scripts/attestation_response_simulator.py have been run.
